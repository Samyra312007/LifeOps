## 2. Detailed Flows

### 2.1 Onboarding Flow

```
START
  │
  ├─► Sign Up (Email + Google OAuth)
  │
  ├─► Connect Data Sources (Step-by-step wizard):
  │     1. Google (Gmail + Calendar + Fit) — OAuth consent screen
  │     2. Bank/Plaid — Link account via Plaid Link
  │     3. Amazon — OAuth or API key
  │     4. DoorDash — OAuth
  │     5. Spotify — OAuth
  │     6. Todoist/Notion — OAuth or API token
  │     7. GitHub — OAuth
  │     8. Strava — OAuth
  │     9. Netflix — Manual or OAuth
  │     10. Uber/Lyft — OAuth
  │
  ├─► Onboarding Survey:
  │     - What are your top 3 goals? (Save money, Sleep better, Be more social, etc.)
  │     - What time do you usually wake up / go to bed?
  │     - Dietary preferences / restrictions
  │     - Current budgeting approach
  │     - How many meetings per week is "too many"?
  │     - Who are your most important contacts?
  │
  ├─► Initial Data Sync (Background):
  │     - Fivetran begins backfill (up to 90 days of history)
  │     - Estimated time: 5–30 minutes depending on data volume
  │     - Progress bar shown to user
  │
  ├─► First Morning Brief (Next day at 7am):
  │     - User receives first full cross-domain brief
  │     - Introduces LifeOps capabilities with examples
  │
  └─► DONE → Dashboard
```

### 2.2 Morning Brief Flow

```
TRIGGER: Daily at 7:00 AM (user's timezone)
  │
  1. Orchestrator calls all data services in parallel:
  │     ├─► Elasticsearch: recent events, yesterday's patterns
  │     ├─► BigQuery: daily aggregations (sleep, steps, spending, meetings)
  │     ├─► MongoDB: user preferences, goals, contact dates
  │     ├─► Pattern Detection Agent: check for active patterns
  │
  2. Context assembler merges results into structured brief payload:
  │     {
  │       sleep: { score: 61, trend: "below_avg", nights_below_6h: 4 },
  │       schedule: { meetings: 4, back_to_back: ["10-1pm"], free_time: [] },
  │       budget: { dining_overage: 87, days_left: 9 },
  │       social: { upcoming_birthdays: [{name: "Jordan", days_away: 2}] },
  │       patterns: { active: ["stress_spiral_early_warning"], confidence: 0.78 }
  │     }
  │
  3. Gemini 2.5 Pro generates natural language brief:
  │     - Synthesizes all sections into coherent narrative
  │     - Generates actionable options for each risk
  │     - Prioritizes by urgency + user's known preference
  │
  4. Delivery:
  │     ├─► Push notification (mobile/desktop) at 7:00 AM
  │     ├─► Full brief available in-app
  │     └─► Optional: email delivery
  │
  5. User Interaction:
  │     ├─► Tap/click an action → Action Execution Flow
  │     ├─► Ask follow-up → Cross-Domain Q&A Flow
  │     └─► Dismiss → Recorded as ignored for self-improvement
  │
  └─► Arize Phoenix trace recorded
```

### 2.3 Cross-Domain Q&A Flow

```
USER: Types a question (e.g., "How am I doing this week?")
  │
  1. Google ADK Orchestrator receives query
  │
  2. Intent Classifier categorizes:
  │     - Domains involved (health, finance, social, productivity)
  │     - Query type (status, prediction, advice, historical)
  │     - Urgency (routine vs. critical)
  │
  3. Query Planner decomposes into sub-queries:
  │     ├─► Elasticsearch: "this week sleep scores, workout frequency"
  │     ├─► BigQuery: "this week spending vs budget, transactions"
  │     ├─► MongoDB: "current goals, last week's priorities"
  │     ├─► Elasticsearch: "social events, emails about commitments"
  │
  4. Parallel execution of all sub-queries (target: < 1s)
  │
  5. Context Assembler merges results
  │
  6. Gemini 2.5 Pro reasoning:
  │     ├─► Identifies cross-domain correlations
  │     ├─► Detects anomalies (e.g., "you're stressed and spending more")
  │     ├─► Generates response with synthesized view
  │     └─► Proposes specific actions with One-Tap buttons
  │
  7. Response delivered to user
  │
  8. Arize Phoenix trace recorded:
  │     - Query, retrieved context, generated response, user action
  │
  └─► User can follow up → Repeat from step 1
```

### 2.4 Proactive Pattern Detection & Alert Flow

```
RUNS: Continuously (event-driven, every 30 min)
  │
  1. Pattern Detection Agent evaluates latest data:
  │     ├─► Sleep trend (3+ nights < 6h?)
  │     ├─► Meeting load (weekly total > sustainable limit?)
  │     ├─► Spending velocity (dining > budget pace?)
  │     ├─► Exercise gap (no workout > 5 days?)
  │     ├─► Social isolation (no social events > 10 days?)
  │     ├─► Work intensity (GitHub commits late night spikes?)
  │     ├─► Composite: known stress spiral signature?
  │
  2. If pattern confidence > threshold (0.7):
  │     ├─► Check if already alerted this cycle
  │     ├─► Generate intervention
  │     │     - Based on past successful interventions (from MongoDB)
  │     │     - Include 1-3 specific, actionable options
  │     └─► Queue notification
  │
  3. Alert delivered:
  │     ├─► "Heads up — I'm seeing your stress spiral pattern..."
  │     └─► Options: "Yes, do it" | "Not now" | "Tell me more"
  │
  4. User Response:
  │     ├─► "Yes, do it" → Action Execution Flow
  │     ├─► "Tell me more" → Expanded reasoning with data
  │     └─► "Not now" / Ignore → Record for improvement
  │
  └─► Arize Phoenix trace recorded
```

### 2.5 Action Execution Flow

```
TRIGGER: User approves an action (tap "Do it" or "Yes")
  │
  1. Orchestrator identifies action type:
  │     ├─► Calendar action (move/reschedule/block)
  │     ├─► Email action (send reminder, cancel subscription)
  │     ├─► Shopping action (place Instacart/Amazon order)
  │     ├─► Finance action (cancel subscription, transfer funds)
  │     ├─► Notification action (send reminder to self)
  │
  2. Action Agent prepares execution:
  │     ├─► Gather necessary parameters (from context)
  │     ├─► Validate preconditions (budget, availability, conflicts)
  │     ├─► Present final confirmation to user
  │
  3. User confirms (final tap)
  │
  4. Action Agent executes:
  │     ├─► Google Calendar API (create/update events)
  │     ├─► Gmail API (send emails)
  │     ├─► Plaid API (cancel subscription via linked card)
  │     ├─► Instacart/Amazon API (place order)
  │     ├─► Todoist API (create task)
  │
  5. Verification:
  │     ├─► Confirm execution via API response
  │     ├─► If failure → Retry (max 3) → Notify user
  │
  6. Confirmation to user:
  │     ├─► "Done! I've blocked your calendar and ordered dinner."
  │     └─► Links to see changes
  │
  7. Arize Phoenix trace recorded:
  │     - Action taken, APIs called, success/failure, outcome
  │
  └─► Memory updated in MongoDB
```

### 2.6 Self-Improvement Loop Flow

```
TRIGGER: Weekly (every Sunday at 2 AM)
  │
  1. Self-Improvement Agent queries Arize Phoenix:
  │     ├─► All traces from past 7 days
  │     ├─► Aggregate by domain
  │     ├─► Calculate follow-through rates per domain
  │     ├─► Calculate outcome scores per domain
  │
  2. Analysis:
  │     ├─► "Health recommendations: 34% follow-through rate"
  │     ├─► "Financial recommendations: 85% follow-through rate"
  │     ├─► "Most ignored: vague health advice"
  │     ├─► "Best performing: specific, immediate actions"
  │
  3. Gemini 2.5 Pro generates improvement plan:
  │     ├─► Adjust prompt templates for low-performing domains
  │     ├─► Change recommendation style (more specific, less preachy)
  │     ├─► Update pattern detection thresholds
  │     ├─► Modify alert timing preferences
  │
  4. Updates applied to system:
  │     ├─► Agent prompts updated in ADK
  │     ├─► Scoring weights adjusted
  │     ├─► New behavior configuration saved
  │
  5. Summary report generated (internal):
  │     ├─► Week-over-week improvement metrics
  │     ├─► Store in Arize Phoenix as trace
  │
  └─► Next week: repeat with updated configuration
```

```
                     │              │                        │
                     ▼              ▼                        ▼
                 ERROR ──────────► ERROR ◄────────────── ERROR
                     │              │                        │
                     ▼              ▼                        ▼
               DISCONNECTED ◄─── DISCONNECTED ◄───────── DISCONNECTED
```

### 4.2 Morning Brief State

```
SCHEDULED
    │
    ▼
GATHERING_DATA (parallel fetch from 3+ services)
    │
    ▼
SYNTHESIZING (Gemini generates narrative)
    │
    ▼
READY_FOR_DELIVERY
    │
    ├─► DELIVERED (user received)
    ├─► INTERACTED (user tapped action)
    └─► EXPIRED (30 min, no interaction)
```

```
PENDING_APPROVAL
    │
    ├─► USER_APPROVED → EXECUTING → VERIFYING → COMPLETED
    │                                       └──► FAILED → RETRYING → COMPLETED
    │                                                                   └──► FAILED
    │
    └─► USER_REJECTED → CANCELLED
```

## 5. Notification Decision Tree

```
New Data Arrives
  │
  ├─► Is this the user's briefing time? → YES → Send Morning Brief
  │                                          NO  → Continue
  │
  ├─► Does this data match an active pattern? → YES → Check alert cooldown
  │                                                     ├─► Within cooldown? → Queue for next window
  │                                                     └─► Outside cooldown? → Send Pattern Alert
  │                                                NO  → Continue
  │
  ├─► Is this an urgent detected event? → YES → Check user's "do not disturb"
  │                                              ├─► DND active? → Queue
  │                                              └─► No DND → Send Critical Alert
  │                                         NO  → Continue
  │
  └─► Log data point → Update patterns → Wait for next cycle

Alert Cooldown Rules:
  - Same pattern: max 1 alert per 48 hours
  - Same domain: max 2 alerts per day
  - Critical alerts: no cooldown, immediate delivery
  - Briefing hour: no non-critical alerts sent within 30 min of briefing
```
