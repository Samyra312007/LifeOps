## 1. System Architecture Overview

LifeOps is a cloud-native, event-driven system composed of six major layers:

```
┌─────────────────────────────────────────────────────────┐
│                    Presentation Layer                     │
│              Web App (React) + Push Notifications         │
├─────────────────────────────────────────────────────────┤
│                   Orchestration Layer                     │
│            Google ADK — Multi-Agent Coordination          │
├─────────────────────────────────────────────────────────┤
│                    Intelligence Layer                     │
│     Gemini 2.5 Pro — Cross-Domain Reasoning & Planning    │
├─────────────────────────────────────────────────────────┤
│                    Memory Layer                           │
│   MongoDB Atlas (User Memory) + Elasticsearch (Search)    │
├─────────────────────────────────────────────────────────┤
│                    Data Layer                             │
│     Google BigQuery (Warehouse) + Fivetran (Ingestion)    │
├─────────────────────────────────────────────────────────┤
│                    Source Layer                           │
│    Gmail · Calendar · Fit · Plaid · Amazon · DoorDash     │
│    Spotify · Todoist · GitHub · Strava · Netflix · Uber   │
└─────────────────────────────────────────────────────────┘
│                    Observability Layer                    │
│              Arize Phoenix — Tracing & Self-Improvement   │
└─────────────────────────────────────────────────────────┘
```

## 3. Data Flow Architecture

### 3.1 Ingestion Pipeline

```
Source Apps
    │
    ▼ via OAuth
Fivetran Connectors
    │
    ▼ CDC (Change Data Capture)
BigQuery Raw Layer (fivetran_* schemas)
    │
    ▼ dbt Transformations
BigQuery Enriched Layer (enriched_* schemas)
    │
    ▼ Extract
Elasticsearch Index (hybrid search ready)
    │
    ▼ Summarize
MongoDB Atlas (user memory graph)
```

**SLA:** Data latency < 15 minutes for critical apps (Calendar, Email, Bank).  
**Non-critical apps:** hourly sync.

### 3.2 Query/RAG Flow

```
User Query (Natural Language)
    │
    ▼
Google ADK Orchestrator
    │
    ├─► Intent Classifier
    │       │
    │       ▼
    │   Multi-Domain Query Planner
    │       │
    │       ├─► Elasticsearch — hybrid search across all domains
    │       ├─► MongoDB — fetch user memory context
    │       ├─► BigQuery — real-time data aggregations
    │       │
    │       ▼
    │   Context Assembler (synthesizes results)
    │       │
    │       ▼
    ├─► Gemini 2.5 Pro — reasons across assembled context
    │       │
    │       ▼
    ├─► Response Generator — natural language + actionable options
    │       │
    │       ▼
    ├─► Arize Phoenix Trace — records full trace
    │
    ▼
User Receives Response
```

### 3.3 Action Execution Flow

```
User Approves Action
    │
    ▼
Google ADK Action Agent
    │
    ├─► Determine Required API Calls
    ├─► Execute (e.g., Calendar API, Gmail API, Plaid API)
    ├─► Verify Execution
    │
    ▼
Confirm to User
    │
    ▼
Trace in Arize Phoenix
```

## 4. Component Specifications

### 4.1 Data Ingestion (Fivetran + BigQuery)

**Requirements:**
- Fivetran connectors for: Gmail, Google Calendar, Google Fit, Plaid, Amazon, DoorDash, Spotify, Notion/Todoist, GitHub, Strava, Netflix, Uber/Lyft
- OAuth 2.0 token management with automatic refresh
- BigQuery raw tables per connector with standard schemas
- dbt transformation layer for enrichment, deduplication, and cross-domain joins
- Data quality monitoring — alerts for stale/empty syncs

**BigQuery Table Design:**
```
fivetran_gmail.messages
fivetran_calendar.events
fivetran_fit.sleep_sessions
fivetran_fit.steps
fivetran_plaid.transactions
fivetran_amazon.orders
fivetran_doordash.orders
fivetran_spotify.play_history
fivetran_todoist.tasks
fivetran_github.events
fivetran_strava.activities
fivetran_uber.rides
```

### 4.2 Search & Retrieval (Elasticsearch)

**Requirements:**
- Hybrid search: semantic (dense vector) + keyword (BM25) retrieval
- Index per domain + cross-domain composite index
- Real-time indexing from BigQuery enrichment layer
- Reranking for relevance scoring

**Index Structure:**
```
Index: user_domain_events (per domain, per user)
  - id, user_id, domain, timestamp, vector_embedding, text_content, metadata
Index: user_cross_domain (aggregated for cross-domain queries)
  - id, user_id, domains[], timestamp, vector_embedding, text_content, domain_summaries
```

### 4.3 Memory Layer (MongoDB Atlas)

**Requirements:**
- Document store for user profiles, preferences, and long-term memory
- Graph-like references for relational memory (e.g., relationships, pattern sequences)
- TTL indexing for ephemeral data; permanent storage for memory
- Vector search capability for memory similarity

**Collections:**
```
users
  - _id, created_at, data_connectors[], preferences{}, goals{}

user_memories
  - _id, user_id, memory_type, domain, content, embedding, created_at, importance_score, access_count

user_patterns
  - _id, user_id, domain, pattern_type, description, confidence, occurrences, last_observed

user_relationships
  - _id, user_id, contact_id, name, last_contact, important_dates[], preferences{}, notes

user_decisions
  - _id, user_id, query, recommendation, action_taken, outcome, timestamp, trace_id
```

### 4.4 AI Reasoning (Gemini 2.5 Pro + Google ADK)

**Requirements:**
- Agent orchestration for multi-domain query planning
- Function calling for structured data retrieval
- Context window management (system prompt + retrieved data)
- Chain-of-thought reasoning for complex queries
- Safety filters and hallucination guards

**Agents:**
| Agent | Responsibility |
|-------|---------------|
| Orchestrator | Receives input, classifies intent, delegates to sub-agents |
| Query Planner | Decomposes complex queries into sub-queries across domains |
| Morning Brief Agent | Daily 7am briefing generation |
| Pattern Detection Agent | Monitors for known stress/financial/social patterns |
| Action Agent | Executes approved actions (calendar, email, subscriptions) |
| Self-Improvement Agent | Weekly Arize trace analysis and behavior update |

### 4.5 Observability & Self-Improvement (Arize Phoenix)

**Requirements:**
- Trace every AI decision with full context
- Record user follow-through (action taken or ignored)
- Weekly automated analysis of trace data
- Model evaluation scores for recommendation quality
- Automated prompt/strategy updates based on analysis

**Trace Schema:**
```
trace_id, user_id, timestamp, query, domain, retrieved_context_ids,
llm_response, structured_options[], user_action{none|option_selected},
follow_through_observed, outcome_quality{1-5}
```

## 5. API Contracts

### 5.1 User-Facing API (Presentation → Orchestration)

```
POST /api/query
  Body: { query: string, context?: {} }
  Response: { response: string, options: ActionOption[], trace_id: string }

POST /api/execute
  Body: { trace_id: string, action_id: string }
  Response: { status: string, result: {}, confirmation: string }

GET /api/brief
  Query: { user_id: string }
  Response: { brief: BriefSection[], generated_at: timestamp }

GET /api/patterns
  Query: { user_id: string, domain?: string }
  Response: { patterns: Pattern[], alerts: Alert[] }

POST /api/connectors/sync
  Body: { user_id: string, connector_id: string }
  Response: { status: string, records_synced: number }
```

### 5.2 Internal Service APIs

```
(Orchestrator → Data Services)

GET /data/search
  Query: { user_id, query, domains[], top_k }
  Response: { results: SearchResult[] }

GET /data/memory
  Query: { user_id, memory_types[], limit }
  Response: { memories: Memory[] }

POST /data/memory
  Body: { user_id, memory_type, content, importance }
  Response: { memory_id: string }

GET /data/analytics
  Query: { user_id, domain, metric, time_range }
  Response: { data: TimeSeriesPoint[] }
```

### 5.3 Data Connector Interface

```
interface DataConnector {
  connector_id: string;
  source: string;
  sync(): Promise<SyncResult>;
  transform(raw: any): EnrichedRecord;
  validate(record: EnrichedRecord): boolean;
}
```

## 6. Infrastructure Requirements

### Compute
- **Google Cloud Run:** 2 vCPU / 4GB RAM per instance, min 2 instances, max 50
- **Auto-scaling:** Based on CPU > 60%, concurrent requests > 100
- **Regions:** us-central1 (primary), europe-west1 (DR)

### Storage
- **BigQuery:** 50TB initial allocation, auto-scaling
- **MongoDB Atlas:** M30 cluster (2 vCPU, 8GB RAM), 100GB storage
- **Elasticsearch:** 3-node cluster (2 vCPU, 8GB RAM each)

### Networking
- Cloud CDN for static assets
- VPC with private service networking for data services
- TLS 1.3 for all API traffic
- API Gateway for rate limiting and auth

### Security
- OAuth 2.0 for all third-party data sources
- JWT-based session management
- Row-level security in BigQuery
- Encryption at rest (AES-256) and in transit (TLS 1.3)
- SOC 2 Type II compliance target

## 8. Monitoring & Alerting

- **Service health:** Cloud Monitoring dashboards per service
- **Alert thresholds:** Error rate > 1% over 5min, latency > P95 threshold, sync failures > 3 consecutive
- **Trace sampling:** 100% of LLM traces; 10% of search traces
- **Logging:** Cloud Logging with structured JSON, retention 30 days
- **Cost monitoring:** Per-connector BigQuery cost, per-user AI cost, total infrastructure burn rate

## 9. Compliance & Privacy

- GDPR right-to-erasure implementation across all data stores
- Data retention policies: raw data 90 days, enriched data 12 months, memory permanent (until deletion request)
- User data export endpoint (GDPR Article 20)
- Privacy policy transparency: all data sources, all storage locations, all AI model usage
- No training on user data without explicit opt-in
